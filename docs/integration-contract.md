# cluster-api-hypervisor — k8labs Integration Contract

This document defines the migration boundary between the k8labs project and the
cluster-api-hypervisor provider: which k8labs flows are retired, which host
networking responsibilities move to the provider, which new flows replace them,
and what stays unchanged. It is the contract the k8labs-side `mgmt` module and
the k8labs Makefile migration follow.

Every target name below is read from the actual k8labs Makefile
(`k8labs/Makefile`, i.e. `/home/eryoma/workspace/k8labs/Makefile`); the source
line of each target is listed so the contract can be re-verified. Targets that
are genuinely new (they do not exist in the Makefile yet) are marked as such.

Source files:

- `k8labs/Makefile` — retired, replaced, and unchanged targets.
- `templates/clusterclass.yaml` — the committed ClusterClass template used by
  the new cluster create/delete flows.

---

## 1. Retired flows and targets

The following k8labs flows are retired. Their responsibilities move into CAPI
objects (Cluster/Machine/etc.) reconciled by the provider; node identity stops
being driven by OpenTofu state.

| Retired flow | k8labs target(s) | Makefile source | Replaced by |
|---|---|---|---|
| Terraform phase A (VM provisioning) | `deploy`, `destroy`, `cluster` (its phase-A step) | `k8labs/Makefile:352` (`deploy`), `k8labs/Makefile:357` (`destroy`), `k8labs/Makefile:519` (`cluster`) | `Cluster` + `Machine` objects applied from the committed ClusterClass template; VMs become provider-owned processes |
| Terraform phase B (`terraform/runtime/`) | `runtime-tfvars`, `configure` | `k8labs/Makefile:490` (`runtime-tfvars`), `k8labs/Makefile:495` (`configure`) | HypervisorControlPlane / HypervisorConfig / HypervisorMachineTemplate controllers render PKI, kubeconfigs, encryption config, and confext disks in Go |
| Per-VM root disk creation | `vm-disks` | `k8labs/Makefile:313` | The Machine controller creates the root disk (`qemu-img convert` + resize) from the base image when reconciling a Machine |
| Single deploy command | `deploy` | `k8labs/Makefile:352` | `kubectl apply` of the Cluster object (or `make mgmt-up` + Cluster apply) |
| Node identity source of truth | `build/deploy.tfvars` (target `tfvars`) | `k8labs/Makefile:300` (`TFVARS := build/deploy.tfvars`), `k8labs/Makefile:302` (`tfvars`) | Node identity (name/CPU/RAM/disk) moves into CAPI objects: `Cluster`, `MachineDeployment`/`Machine`, `HypervisorMachineTemplate` |
| VM process lifecycle over TF-owned sockets | `start`, `stop` | `k8labs/Makefile:369` (`start`), `k8labs/Makefile:384` (`stop`) | Machine controller keeps the VM process aligned with the Machine object (boot/shutdown on reconcile, delete tears the VM down) |

Notes on retired artifacts:

- `deploy` (`k8labs/Makefile:352-355`) runs `tofu -chdir=terraform apply`
  against the phase-A root module; `destroy` (`k8labs/Makefile:357-365`) and the
  `cluster` target's phase-A step (`k8labs/Makefile:524`) are the same pipeline.
- `configure` (`k8labs/Makefile:495-501`) runs
  `tofu -chdir=terraform/runtime apply`; `runtime-tfvars`
  (`k8labs/Makefile:490-493`) derives its inputs from tofu output and DHCP
  leases — both inputs disappear with phase A.
- `destroy-full` (`k8labs/Makefile:398-420`) removes `terraform/runtime`
  state, `build/runtime`, `build/vm-disks`, certs, and the root `kubeconfig`;
  its cleanup role is taken over by Machine/Cluster deletion and the provider's
  teardown.
- `vm-disks` (`k8labs/Makefile:313-350`) produces
  `build/vm-disks/<name>-root.qcow2` from `build/k8labs-base.qcow2`; the
  provider consumes the same base image but creates disks under its own
  `HYPERVISOR_VM_DISKS_DIR` (default `build/vm-disks`), so the artifacts are no
  longer Makefile-owned.

## 2. Replaced host networking

The per-node and bridge networking that `make network-up` used to install is
now owned by the k8netd userspace daemon; the provider drives it through the
k8netd control socket:

| Responsibility (old owner) | Old mechanism | Makefile source | New owner |
|---|---|---|---|
| Per-node TAPs | `network-up` installs per-node systemd-networkd TAP configs generated by `nodes-generate` (`scripts/gen-network.py` -> `build/network`) | `k8labs/Makefile:155` (`nodes-generate`), `k8labs/Makefile:163` (`network-up`) | k8netd via vhost-user port sockets (one port per Machine, attached to the cluster network) |
| Bridge `k8sbr0` | `network-up` copies `network/k8sbr0.netdev` / `network/k8sbr0.network` to `/etc/systemd/network/` | `k8labs/Makefile:166` | k8netd userspace vhost-user L2 switch (created/removed with the cluster network; no host interface) |
| DHCP | systemd-networkd `k8sbr0.network` serves DHCP `192.168.124.20-200` | `k8labs/Makefile:193` | k8netd DHCP server on the network gateway, honoring AllocateIP reservations |
| DNS forwarder | `network-up` installs `/etc/dnsmasq.d/k8sbr0.conf` and activates dnsmasq | `k8labs/Makefile:174-192` | k8netd DNS forwarder served on the gateway IP, pinned upstream resolvers |
| NAT / forwarding | `network-up` loads `network/nat.nft` into the scoped `inet k8slab` nftables table | `k8labs/Makefile:173` | Per-VM passt WAN instances (egress plus explicit inbound port forwards, e.g. host 6443 -> control-plane VM) |
| Teardown | `network-down` removes systemd-networkd configs, the dnsmasq conf, and the `inet k8slab` table | `k8labs/Makefile:195-207` | Provider teardown on Cluster deletion via k8netd DeleteNetwork/DeletePort — no host network state exists to clean up |

Rootless **host prerequisites** (the lab user in the `kvm` group, the k8netd
user quadlet with its passt binary, and any base image/firmware staging the
quadlets need) become the `mgmt` module's responsibility; the provider assumes
the k8netd control socket (`/run/user/<uid>/k8snet/control.sock`) is reachable
and reconciles the cluster network through it.

## 3. New flows

| New flow | Target / object | Status in `k8labs/Makefile` | What it does |
|---|---|---|---|
| Management plane up | `make mgmt-up` | New — does not exist in the Makefile today | Starts the `mgmt` module (podman quadlets: management apiserver + provider) on the lab host |
| Management plane down | `make mgmt-down` | New — does not exist in the Makefile today | Stops the management quadlets cleanly |
| Cluster create / delete | ClusterClass template + Cluster object | `templates/clusterclass.yaml` (ClusterClass `hypervisor-cluster-template`, `templates/clusterclass.yaml:18`) | Operator applies the committed ClusterClass and a Cluster (e.g. `templates/cluster-example.yaml`); provider creates Machines, VMs, disks, and networking; deleting the Cluster object tears everything down |
| Kubeconfig fetch | `make kubeconfig` | `k8labs/Makefile:582` (unchanged target name) | Repurposed: reads the `<cluster>-kubeconfig` Secret from the management cluster (written by HypervisorControlPlane after apiserver healthz) instead of SSH-fetching `admin.kubeconfig` from the control-plane VM |
| IP wait | `make wait-ips` | `k8labs/Makefile:422` (retired semantics) | Superseded: read `Machine.status.addresses` instead of polling DHCP lease files |
| SSH wait | `make wait-ssh` | `k8labs/Makefile:449` (retired semantics) | Superseded: `Machine.status.addresses` plus node Ready conditions replace lease-file + SSH polling |

New targets (`mgmt-up`, `mgmt-down`) are additions the `mgmt` module provides;
the k8labs migration must add them. `kubeconfig` keeps its target name but its
implementation changes to a management-cluster Secret read.

## 4. Unchanged flow

| Flow | Target | Makefile source | Status |
|---|---|---|---|
| Workload-cluster acceptance gate | `make smoke-test` | `k8labs/Makefile:613` | Unchanged — remains the gate for the workload cluster (nodes Ready, kube-system pods Running, Cilium health, Gateway, CoreDNS regressions) |

`smoke-test` (`k8labs/Makefile:613-792`) runs against the workload cluster
kubeconfig and stays the acceptance gate for the end-to-end flow:
mgmt-up -> create Cluster -> VMs boot -> all nodes Ready -> smoke-test passes.

| Retired target | Makefile source | Replacement |
|---|---|---|

End-to-end result after the migration: `make mgmt-up` -> apply ClusterClass +
Cluster -> VMs boot -> `make smoke-test` passes, with no `tofu` invocation, and
node identity changes (add a worker) converge through CAPI objects only.
